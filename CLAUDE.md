# AI Software Factory

A local dashboard that shows real AI coding agents as robots in a 3D factory.
The 3D scene only displays state. The backend owns agent execution, process
management, and status.

## Rules

- Never show fake results. If an agent can't do something, mark it unsupported.
  Mock or replay data must be clearly labelled.
- Bind the local service to 127.0.0.1 and check `Origin` on requests.

## Stack and layout

- Web app: Vite + React 19 + TypeScript + React Three Fiber + drei, in `apps/dashboard/` (not Next.js).
- Start everything: double-click `start-factory.bat` at the repo root (installs packages on first run, starts the agent service on 4317 and the dashboard on 5173 in two windows, skips a port that is already in use, opens the page).
- Settings: the ⚙ Settings dialog (`SettingsPanel.tsx`) has Projects (hide a project from the sky and tabs, rename it for display), Agents (days back, extra folders, service status), Display (quality, frame-rate counter, glass blur, labels all/names/none, motion), Sound & camera (sound, volume, idle-tour delay) and About. Everything is saved in one JSON file, `~/.ai-factory/settings.json`, by the service (`settings.ts`, `GET/PUT /api/settings`; a change needs an allowed Origin or the bearer token; a whole change applies or none of it; the file is written through a temp file); display choices also live in the browser (`uiSettings.ts`, `uiStore`/`useUi`, synced by `live/useSettingsSync.ts`; the file wins when the page connects). Hidden projects free their place, so the next project comes in (still at most 8).
- Agent service: `apps/agent-service/` (Node 22, TypeScript, no runtime dependencies, `npm start`, port 4317, binds 127.0.0.1, checks `Host` and `Origin`; design in `docs/superpowers/specs/2026-11-08-agent-service-design.md`, usage in its README). It only watches, read-only: Claude Code transcripts (`~/.claude/projects`), Codex (`~/.codex/state_5.sqlite` + rollout files), GitHub Copilot Chat (VS Code `chatSessions`), and any other agent through `POST /api/hook` (bearer token in `~/.ai-factory/token`, helper `scripts/report.mjs`). Per project it reports sessions (state is inferred and says so: `status.ts`), a roster of every agent that exists, working or not (`roster.ts`: agent files of the three tools, sessions and subagent runs; a run is matched to its agent file by type name; Claude runs come from `<session>/subagents/`, Codex runs from subagent threads, Copilot subagent runs are not read; `AGENT_SERVICE_DAYS` sets how far back), the department of the newest tool (`department.ts`), MCP servers (`mcp.ts`; env values never read) and harness items (`harness.ts`). Folders with agent setup files but no recent session are found by `discover.ts` (next to folders where agents were used, or `AGENT_SERVICE_ROOTS`) and shown as idle projects (`discovered: true`, max 8 projects). Sample projects for testing, one per harness (Aurora Shop = Claude Code, Ledger API = Codex, Nimbus Portal = GitHub Copilot, Orbit Lab = all three; 15 sample agent roles in total) live in `E:\work\` outside this repo; each has a README saying it is sample data, and the hub shows them only as idle projects found by their setup files, never as agents that ran. Starting/stopping/prompting agents is marked `control: unsupported`. The hub shows the whole crew (`apps/dashboard/src/crew.ts`, `CrewList.tsx`): one robot per roster entry in its bay (3 desks, `+N more` badge for the rest); working = lit eyes and its work animation, waiting for you = amber tag and waving, idle = asleep in a rest bunk (dim eyes), standby = defined in an agent file but no run seen (eyes off, also in a rest bunk). The bay of a standby agent is a guess from its name, description or tools and the panel says so (`departmentBasis`); once it runs its real activity decides. There are three departments (planning, development, review): commit, push, deploy and release work count as development. Account-level agents (`~/.claude/agents`) get a desk only after they ran in the project. A robot's shape comes from a hash of its agent and name, so it stays the same; demo projects keep seating working robots from counts. Message text, tool inputs and results are never sent. The dashboard side is `apps/dashboard/src/live/` (`useLive` follows `/api/events`, `liveProjects.ts` maps a snapshot to `Project`, `parseSnapshot` validates it), `ProjectInfoPanel.tsx` (button "Project info") and the live variant of `DepartmentPanel`. The banner says LIVE or LOOK TEST; with the service off the labelled demo projects show, and starting it later flips the page to live by itself; `?live=off` forces the demo, `?service=` points at another local port. Live projects have `source: 'live'`; progress is the agents' own task list (`TodoWrite` / `update_plan`) or 0 with `planKnown: false`, never a made-up number; scene number labels end in `dataTag(project)` (demo / agent plan / no plan data). Belts, the drone and the weather stay decoration. Scene components get the project list as a prop (React context does not cross into the Canvas); `projectsContext.ts` is for DOM parts only.
- 3D assets: built in Blender through MCP (safe mode), scripts in `assets/source/`, exports in `assets/models/`, copies in `apps/dashboard/public/models/`.
- The scene is a round command hub: an arc-reactor core, three open bays side by side on the ring (Planning, Development & Integration, Review & QA; Review and QA were merged, and Integration was folded into Development on 2026-11-10; each merged bay shows both signs and the props of both jobs, its robots doing both by seat via `seatJob`) and the rest bunks round the core, glowing branches to every desk. Layout lives in `apps/dashboard/src/hubLayout.ts` (`DEPARTMENTS` types in `hallLayout.ts`). Specs and plans are in `docs/superpowers/`.
- Views: `/` is the hub, `?focus=<department>` frames one bay, `?focus=studio|orb|cart` frames the design studio, the core or the cart, `?scene=robots` shows all robot shapes. Press R to reset the camera, G for the solar system (there is no separate sky view any more: the solar system shows all projects). The hall floats on a rock in space; the project rail on the left (`ProjectRail.tsx`, `rail.ts`: grouped needs you / working / resting with waiting and working counts, `[` folds it) or a planet in the solar system flies to a project; picture mode (`pictureMode.ts`, `H`, Esc leaves) fades out every bar, panel and label; `?project=<id>` opens one, `?focus=sky` frames the hall against the sky (the lift-off view, `skyCamera` in `skyLayout.ts`, where the flights to and from the solar system start and end; the sun and the Milky Way are placed for it); `?focus=system` opens the solar system. Demo projects are in `apps/dashboard/src/projects.ts` and are labelled as demo data. Click a bay to fly in and open its side panel (Esc closes); the buttons bottom left jump to Core, Studio, Cart and System. The hall has no tall wall or roof: `Shell` cuts everything above the floor off the baked mesh (`shellCut.ts`) and `ParapetRing.tsx` (shape in `parapet.ts`) adds a low thick parapet with a glowing status strip and light posts; `EnergyDome.tsx` (`dome.ts`) is a faint shield bubble that fades out as the camera gets close. Click any robot and it plays a gesture picked at random from its own tastes (`gestures.ts`: dance, cheer, bow, shrug, flex, salute, spin; four quick clicks give an excited spin); robots that walk stop while it plays. Every seat in every bay gets a random shape from ten (`bayShapes.ts`: the five department robots plus Terminal head, Gauge bot, Plug, Cassette and Fishbowl), and seated robots take small breaks of their own (`breakAt`). Couriers, crawlers, the cart and the drone move naturally (`couriers.ts` and `crawlers.ts` are small simulations: eased speed, pauses, look-arounds, turn-backs, a high five when the couriers meet). A camera tour (`tour.ts`, `IdleTour.tsx`) starts after 30 s with nothing touched and glides to every bay, the launch pad, library, studio, core, cart and sky; any mouse move, click, wheel, key or touch stops it (`STOP_FLIGHT_EVENT` in `HubCamera.tsx`), it waits while a panel is open or a project is changing, and the Tour button, `?tour=off` or a reduced-motion setting turn it off. Sound follows what you look at (`soundFocus.ts`: the point the camera orbits decides which element has the focus (core, a bay, studio, launch pad, library, belt, or the whole hall), only that element's sounds are in the mix and the rest fade out in about 0.35 s; robot click tunes always play; `sound.workshop(level, position, category)` only asks, and the focused element gets the shared machine loops; the button shows what is being heard). Sound (`sound.ts` has the tested numbers, `soundEngine.ts` makes everything with Web Audio, no files, `SoundDirector.tsx` feeds it the camera) is off until the Sound button is pressed (then a volume slider appears, remembered between visits; `masterGain` and `DEFAULT_VOLUME` in `sound.ts`): core hum, key taps near a busy bay, a small tune per click gesture, and a workshop round the launch pad that is heard only near it (`nearGain`, `sound.workshop()`: weld arc made of random crackle clicks, a frying sizzle, a mains buzz and a zap on striking, crane and turntable motors, the drone's rotors, plus a clunk when a section lands, countdown beeps and a lift-off rumble); `window.__sound.level()` reads the output level for browser checks and `window.__camera` is the camera. `?fx=noao,noshadow,nobloom,lowdpr,noweather` switches effects off to measure what each costs. The Quality button (bottom right) cycles Auto, High, Balanced, Fast and Lite (`quality.ts`, `qualityContext.ts`): Auto starts lower on a weak or software-only graphics chip (`classifyRenderer`, read from the browser's renderer name) and steps down by itself when the frame rate stays low; `?quality=lite` forces a level. The ambient-shading effect is the costliest thing to keep. Lite is for computers with no graphics card: no shadows, glow, blur, shield dome, weather or extra lights, plain robot materials, lower render resolution and no glass blur on the panels (`body[data-quality]` in `index.css`); parts with a cheaper way to draw read the settings with `useQuality()`. Extra scenery: `ReactorCore.tsx` is the core: orb, armour-plate shell, bands, three rings with pods, a halo of data tiles, a stepped vented pedestal with prongs and a ring of status lights, motes and a beam; space around the hub has three themes picked in Settings (`themes.ts`: Deep space, Nebula, Aurora planet; `makePhotoSky` in `skyMaterials.ts` wraps a real Milky Way photo round the scene: NASA SVS "Deep Star Maps 2020" turned into `public/textures/milkyway-4k.jpg` and `-2k.jpg` (credit in `public/textures/CREDITS.md` and Settings > About; the shader decodes the sRGB itself, so the texture is left `NoColorSpace`), graded per theme (`photoExposure`, `photoTint`) with faint nebula gas on top; `spaceScene.ts` turns the photo so the band crosses the sky view (`skyMapToWorld`) and places the sun (`SUN`, a key light plus a glow) and the ringed gas giant (`GIANT`, `FarSpace.tsx`; Deep space and Nebula only) and the lens-flare ghosts (`flareGhosts`, only seen from the sky view); the film finish (flare, grain, vignette) is `film` in `quality.ts`, off in Lite, and `?fx=nofilm` switches it off; colours added on top of the photo are linear and must stay tiny; the camera far plane is 700 for the giant), and `SpaceWeatherLayer.tsx` (`spaceWeather.ts`) draws space weather outside the dome from the project's status: drifting dust when idle, a meteor shower while agents work, ion-storm arcs over the dome when it needs you (no clouds or rain); `ConveyorBelts.tsx` (`belts.ts`) has one belt behind the bays (Development to Integration) that runs with crates only while its source department works, with two robots at it (one inspecting, one stamping, idle when the belt stops); `RocketPad.tsx` (`launchpad.ts`, `rocket.ts`, `WeldBot.tsx`) is the launch pad: the rocket is built from six sections, each lowered by a crane on the tower and welded by a robot on a lift while the rocket turns on a turntable (`weldPlacement` in `rocket.ts` puts the robot where the seam is in reach, and `WeldBot` aims its arm bone after the animation and stretches the torch so the tip is on the seam; `window.__weld.tipError` reads the live error, under 0.2 mm; the robot stands on a work platform with rails that runs out from a carriage on the tower; positions in `weldPlacement` are in the pad's space, so add `ROCKET_BASE` to heights measured on the rocket; a whole rocket builds in 30 s: `REBUILD` in `launchpad.ts`; a crew robot waves from the cabin porthole; `InspectionDrone.tsx` (`inspection.ts`) circles the rocket on the side away from the tower and scans each weld with a laser; only a finished project (Pocket Kit) counts down and launches); how many sections are solid follows the demo progress and the section being fitted loops, and once the demo build is complete the rocket counts down, lifts off and a new one is built; `ArchiveHall.tsx` (`library.ts`, `ShelfBooks.tsx`, `libraryBooks.ts`) is the library against the wall between Planning and Development: three wood-and-steel shelf units under a lit ARCHIVE sign. The shelves hold the project's real markdown files as books (`layoutBooks`, tested): a shelf for every folder with a nameplate (a long folder carries on to the next shelf, marked "(more)"), a book for every file as thick as the file is big, its file name on the spine (one atlas drawn on a canvas, one draw), a pale ribbon on files edited in the last day, at most 150 books (the newest; the Library panel lists all), hover for name, folder, size and age, click to open the file in VS Code; the five newest files float on cards up the glass archive column on the dais. A catalogue desk with a screen and two tending robots stand by (textures are drawn on canvases in code); the old demo crates, their lights and the scanning arm that filed them were removed because they showed a made-up build; `OrbWorkshop.tsx` (`orbArms.ts`, `orbSignal.ts`) has four tool arms (probe, welder, lens, clamp) that sweep over the orb and make it flicker, fold away when idle and point at the bay that needs you; `spinners.ts` turns the cassette's reels and circles the fishbowl's fish (separate pieces fixed to the head bone, built by `assets/source/robot_spin.py`); All of this is demo motion from demo status. The floating panels are frosted glass (`backdrop-filter`). Surface detail is procedural, not big images: `shellDetail.ts` (floor plates, wall rivets and rust, hazard band), `robotLivery.ts` (waist stripe, ID barcode, worn edges), `propWear.ts` (scratches on bay props and crates), `rockMaterial.ts` (island strata and glowing veins), `holoMaterial.ts` (scanline holograms), `skyMaterials.ts` (dome, moon, aurora), all fed by one shared noise texture from `detailNoise.ts`. `Wayfinding.tsx` paints guide strips and an emblem per department on the floor, and `mood.ts` drives the hall light from project status. The parts of a cloned robot share one skeleton (`shareSkeleton` in `mergeSkinned.ts`; separate skeletons each uploaded their bones every frame), shadows are redrawn every other frame (`ShadowThrottle.tsx`, `shadowEvery` in `quality.ts`), tiny and unlit parts do not cast shadows (`shadows.ts`), robots share eye, glow and plain materials; the frame is limited by the processor (three.js draw setup), so fewer separate objects and materials is what speeds it up. Robot parts and static props are merged at load (`mergeSkinned.ts`, `mergeStatic.ts`) to keep draw calls low: put still props inside `StaticMerge`, keep moving parts outside it.
- Solar system level (above the hall; plan in `docs/superpowers/plans/2026-11-10-solar-system-view.md`, look agreed in `docs/superpowers/mockups/space-solar-playground.html`): press G or the System button to fly up from the hall (out to the sky view, fade, then pull back from your own planet); click a planet, or a project in the rail, to fly down into its hall (fly to the planet, fade, come in from the sky view); `?focus=system` opens in it. `level: 'hall' | 'system'` lives in `App.tsx`; `HubScene` keeps the hall mounted but hidden (`visible`) and turns its page labels off, shows `SystemWorld.tsx` and only the sky photo of `SkyWorld` (`system` prop: no sky moon, aurora or planet below), and drops the fog, shadows, ambient shading and zoom blur in that level; `HubCamera` widens its zoom (6 to 420 m), stops clamping the orbit point and resets to `systemCamera`. The star is a fixed red dwarf that stands for this computer (decoration, said so in the label); every project is a planet. All the maths is in `systemLayout.ts` (tested): a kind of world per project (`planetKinds`: eight kinds, each project takes the one its id hashes to or the next free one), orbit radius by place in the project list, planet position over time (`systemTime()`, shared by the scene and the camera flights so a flight ends where the planet really is), `lockedYaw` (tidally locked: the same face to the star), moons from the real crew (`agentCounts`: one green moon per working agent, at most five; one amber moon and an expanding ring when something waits for you; a resting project is dark), `flarePeriod` (the star flares more often when more agents work), `systemCamera` and `planetApproach`. Surfaces are baked once on canvases (`surfaceNoise.ts` wrapping value noise, `planetTextures.ts`: continents and ice caps, craters, lava cracks, dunes, gas bands, a cloud layer and a night-lights map; the star is computed live in its shader, soft boiling granules, dark spots, limb darkening, HDR so the bloom makes it glow; `starTexture.ts` is no longer used) and drawn by small shaders in `systemMaterials.ts` that light themselves from the star at the origin (day side warm, a faint cool fill so the night side still shows, atmosphere and status rim, city lights that blink when it needs you; the star has limb darkening, a second finer layer of cells, a chromosphere rim and a corona billboard with streamers and flares); `prewarmSystem` bakes them quietly after the page loads so the first flight up does not stall. Later stages: the star's magnetic loops and coronal ejections, the other kinds of star (Our Sun, two suns, black hole, blue giant) as a Settings choice, Look closer, and the galaxy of workspaces.
- Hall attention: the "Active now" strip (`ActiveStrip.tsx`, `activeNow.ts`, tested) lists the real agents that work or wait (waiting first, click opens the crew panel; a demo project lists none); a soft light beam from above stands on each working (green) or waiting (amber) agent (`ActiveMarker`); the agents that are asleep (idle) or standing by do not take a desk: they lie in the rest bunks (`BunkRing.tsx`, `restBunks.ts`, tested): up to six low open bunks round the core deck on the camera's side, lying along the ring, only as many as there are sleepers and centred on the front, so never an empty bunk (`BUNKS`, `bunkSpecs(count)`, `restSlots`: asleep agents first, newest sleeper first, then standing by; more than six shows "+N more"), each sleeper lying on its back under a curved glass canopy (a stretched dome, one shared glass material), all heads the same way round; the frost on the canopy is the real time since the agent's last activity (`restFill`, `frostLevel`, tested: clear at first, thickest after 8 hours), the pillow takes the tool colour (same as the moons), the pods have glowing edges and a glowing arc on the floor under them, and a "RESTING" chip shows from far away; there is never an empty pod and a demo project has none. (The canopy does not lift when an agent wakes: the pod simply disappears from the ring when the agent starts working. A first version with tall upright docks was dropped: the camera saw their backs.) Bays therefore seat only working and waiting agents (`crewFor`). The couriers stop at the rest bunks too (with three bays the gap round the ring was over half a turn, so the stop at angle 0 keeps every leg under 180 degrees), the belt from Development just runs out along the edge, and `rest` is a place on the mini-map, in the tour and in the sound focus.
- Solar system polish: every planet carries its name (a small tag; the full status line shows for yours, one that needs you, or the hovered one); the sky photo is dimmed to half in this level; the star has magnetic loops (`starLoops.ts`, tested: arches that rise, hold and fade) and a faint breathing; the view drifts round slowly on its own (about three minutes a turn, off with reduced motion). The hidden hall is paused with React `Activity` while you are in the solar system (its animations stop, its state stays).

- Look closer (solar system): clicking a planet glides the camera to it (`planetApproach`, 1.1 s), then the camera follows the planet round its orbit and `PlanetCard.tsx` shows its real facts (`planetFacts.ts`, tested: status, agents working or waiting, plan %, markdown files, MCP servers, time since last activity; unknown stays "unknown", never made up). A second click or "Enter the hall" goes into the hall; Esc or "Back to the system" glides out (`lookAt`/`lookBack` in `App.tsx`).

Only titles, tool names, counts and times, never messages. A working or waiting agent has a small turning gem with a ripple over its head (`ActiveMarker` in `HubScene.tsx`, green or amber). The core is `RosterCore.tsx` (`coreRoster.ts`): a quiet dark glass sphere and a thin ring with one light per agent (green working, amber waiting and pulsing, grey resting); the old reactor, the four tool arms and the light shaft were removed.

## Skills

Skills in `.claude/skills/` come from Superpowers 7.0.2 (MIT). Use them when the
work calls for it, not on every message:

- New feature or design decision: `brainstorming`, then `writing-plans`
- Running a plan: `subagent-driven-development` or `executing-plans`
- Bugs and failed tests: `systematic-debugging`
- Before saying work is done: `verification-before-completion`

## Testing

Browser smoke test: with the dashboard running, `npm run smoke` in `apps/dashboard` (needs Playwright once: `npm i -D playwright && npx playwright install chromium`) opens the page in a real browser and checks the canvas, the hall and solar system frame rates, planet tags, look closer and Esc, the way back, and that the console has no errors.

Use `test-driven-development` for logic: event parsing, status changes, and
mapping agent activity to departments.

It does not apply to how the 3D scene or UI looks. Check those by running the
app and looking at the result.
